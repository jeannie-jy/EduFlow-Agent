# EduFlow-Agent 远端生产部署方案

## 1. 目标与适用范围

本文给出 EduFlow-Agent 从测试环境到小规模公开服务的完整部署方案，并说明后续向
多副本托管平台演进时需要满足的条件。

当前推荐采用以下两阶段路线：

1. **阶段一：单节点容器化生产部署**。应用容器运行在一台 Linux 主机，数据库、Redis、
   对象存储和密钥管理优先使用托管服务。这是当前代码无需架构改造即可稳定运行的方案。
2. **阶段二：多节点托管容器部署**。API 和 Worker 独立扩容，材料与渲染沙箱迁移到受限
   工作负载。在进入该阶段前，应消除沙箱任务对单机共享卷的依赖。

本文不把仓库根目录的 `docker-compose.yml` 直接视为完整公网生产拓扑。它是本地开发、
集成测试和单节点部署的基础定义；TLS、WAF、托管数据服务、Secret Manager、KMS、备份、
告警和发布控制必须由生产环境补齐。

## 2. 已实现的运行架构

```text
Internet
   |
   v
CDN / WAF / HTTPS Load Balancer
   |
   v
Web (Nginx, React static assets)
   |
   +---- /api/* ----> FastAPI API
                         |-- PostgreSQL + pgvector
                         |-- Redis
                         |-- S3-compatible ArtifactStore
                         |-- KMS Bridge
                         |-- SMTP
                         |-- LLM / Embedding providers
                         |
                         +-- resumable SSE event ledger

Background workloads
   |-- task-worker
   |-- singleton maintenance worker
   |-- material-sandbox (no network, no credentials)
   |-- render-worker (optional)
   `-- render-sandbox (optional, no network, no credentials)

Observability
   `-- OpenTelemetry -> Collector -> metrics / traces / logs
```

关键实现约束：

- API 使用 PostgreSQL 保存业务数据、LangGraph checkpoint、任务 lease 和 SSE 事件账本。
- `task-worker` 可横向增加，但 `maintenance` 必须保持一个实例。
- Alembic 迁移必须在应用发布前作为一次性 Job 执行，不能让每个 API 副本自行迁移。
- `material-sandbox` 与 `task-worker` 当前通过共享卷交换材料解析任务。
- `render-worker` 与 `render-sandbox` 当前通过共享卷交换渲染任务。
- 两类沙箱均不得获得数据库、Redis、对象存储、KMS、SMTP 或模型供应商凭据。
- 生产环境必须使用 BYOK 和远端 KMS Bridge；本地 KEK 仅用于开发。

## 3. 推荐生产拓扑

### 3.1 阶段一：单节点应用 + 托管数据服务

```text
                         +----------------------+
Users -> CDN/WAF/LB ---->| Linux application VM |
                         |  web                 |
                         |  agent-api           |
                         |  task-worker         |
                         |  maintenance         |
                         |  material-sandbox    |
                         |  optional video pair |
                         +----------+-----------+
                                    |
             +----------------------+----------------------+
             |                      |                      |
             v                      v                      v
     Managed PostgreSQL      Managed Redis        Object Storage
       with pgvector                                  / MinIO
             |
             +---- KMS Bridge / SMTP / LLM providers
```

这样部署的原因：

- 保留 Docker Compose 中已经实现的共享卷和无网络沙箱语义。
- 数据服务与应用主机解耦，应用主机损坏后可以快速重建。
- 不需要在首次上线时承担 Kubernetes、RWX 存储和复杂网络策略的运维成本。
- API、任务和视频资源仍然可以通过不同容器设置独立限制。

### 3.2 网络边界

只允许下列公网入口：

| 入口 | 暴露范围 | 说明 |
|---|---|---|
| TCP 443 | 公网 | HTTPS Web 与 `/api` |
| TCP 80 | 公网或关闭 | 只用于跳转到 HTTPS |
| TCP 22 | 管理网/IP 白名单 | SSH 运维；优先通过堡垒机或云控制台 |

下列服务不得暴露公网：

- FastAPI 的 8000 端口；
- PostgreSQL 5432；
- Redis 6379；
- MinIO API 和 Console；
- Prometheus、Grafana；
- `/docs`、`/openapi.json`、`/api/metrics` 和 `/api/metrics/prometheus`。

外部负载均衡必须清除客户端提交的 `X-Forwarded-*` 请求头，再写入可信的
`X-Forwarded-For` 与 `X-Forwarded-Proto`。`TRUSTED_PROXY_IPS` 只能填写真实负载均衡或
反向代理所在的网段，不能使用全网段通配值。

### 3.3 DNS 和域名

推荐使用单一主域名，例如：

```text
app.example.com       Web 与 API
assets.example.com    对象存储签名下载，可选
```

前后端使用同源 `/api`，以简化 Cookie、CORS、CSRF/Origin 检查和 SSE 连接。部署前需要确认：

- `PUBLIC_ORIGIN=https://app.example.com`；
- `AUTH_COOKIE_SECURE=true`；
- `ENFORCE_ORIGIN_CHECK=true`；
- `MINIO_PUBLIC_ENDPOINT` 或对象存储签名地址可以被最终用户访问；
- CDN/负载均衡对 SSE 关闭响应缓冲，并将上游读取超时设置为至少 650 秒。

## 4. 环境与资源规划

### 4.1 操作系统与基础软件

- Ubuntu 24.04 LTS 或同等级受支持的 Linux 发行版；
- Docker Engine 24 或更高版本；
- Docker Compose v2；
- 云主机启用自动安全更新、时间同步和磁盘监控；
- 容器运行目录使用独立磁盘或明确的容量告警。

### 4.2 建议规格

#### 不启用视频导出

| 资源 | 起步配置 | 建议生产配置 |
|---|---:|---:|
| CPU | 4 vCPU | 8 vCPU |
| 内存 | 8 GB | 16 GB |
| 系统盘 | 40 GB SSD | 80 GB SSD |
| 临时/容器盘 | 50 GB SSD | 100 GB SSD |

#### 启用视频导出

| 资源 | 建议配置 |
|---|---:|
| CPU | 8–16 vCPU |
| 内存 | 16–32 GB |
| 临时/容器盘 | 150 GB 以上 SSD |
| 初始视频并发 | 1 |

视频渲染是 CPU、内存和临时磁盘密集型任务。正式开放前必须通过真实课程样例测量单任务的
p50/p95 时间、峰值内存、输出大小和失败率，再决定并发上限。

### 4.3 托管数据服务

PostgreSQL：

- PostgreSQL 16；
- 支持 `pgvector` 扩展；
- 多可用区；
- 存储加密；
- 自动备份和 WAL/PITR；
- 初始连接数按 API 与 Worker 总连接池计算，并保留至少 30% 余量。

Redis：

- 启用传输加密和认证；
- 不允许公网访问；
- 选择具有自动故障转移的托管实例；
- 明确最大内存和淘汰策略；
- Redis 故障时 readiness 应变为失败，但 API 进程不应立即退出。

对象存储：

- 开启版本控制和服务端加密；
- `materials/`、`exports/`、`audit-archives/` 设置不同生命周期；
- CORS 只允许正式站点域名和必要方法；
- 下载默认使用短期签名 URL；
- `audit-archives/` 使用对象锁或等效的不可变保留能力；
- 若替换 MinIO 为云对象存储，必须在 staging 验证当前 MinIO SDK 所需 API 的兼容性。

## 5. 生产配置与 Secret

以 `ops/production.env.example` 作为配置契约，但不要把填入真实值的文件提交到 Git。

### 5.1 必须配置的安全项

```dotenv
ENVIRONMENT=production
PUBLIC_ORIGIN=https://app.example.com
ENFORCE_ORIGIN_CHECK=true
TRUSTED_PROXY_IPS=<load-balancer-private-cidr>
EXPOSE_API_DOCS=false

AUTH_REQUIRED=true
AUTH_COOKIE_SECURE=true
AUTH_ALLOW_REGISTRATION=false
AUTH_REQUIRE_EMAIL_VERIFICATION=true
AUTH_REGISTRATION_CHALLENGE_REQUIRED=true
BYOK_REQUIRED=true

RUN_MAINTENANCE=false
VIDEO_PUBLIC_ENABLED=false

LLM_API_KEY=
EMBEDDING_API_KEY=
```

首次发布建议关闭公开注册和视频。管理员完成验收后，再分别开启这两个功能。

### 5.2 KMS Bridge

生产环境使用：

```dotenv
CREDENTIAL_KMS_BACKEND=http
CREDENTIAL_KMS_WRAP_URL=https://kms-bridge.internal/v1/wrap
CREDENTIAL_KMS_UNWRAP_URL=https://kms-bridge.internal/v1/unwrap
CREDENTIAL_KMS_BEARER_TOKEN=<secret reference>
CREDENTIAL_FINGERPRINT_KEY_B64=<independent secret reference>
CREDENTIAL_KEK_VERSION=<kms-key-version>
```

要求：

- Bridge 只允许 API 和需要解密凭据的 Worker 调用；
- wrap/unwrap 使用不同的审计动作；
- 记录调用者、密钥版本、结果和延迟，但绝不记录明文密钥；
- 旧密钥版本必须保留解包能力，直到所有数据完成轮换；
- 指纹 HMAC 密钥不得与对象存储凭据放在同一 Secret 中。

### 5.3 Secret 注入原则

- 优先使用云 Secret Manager 通过文件或工作负载身份注入；
- 禁止将 Secret 写入镜像、Git、CI 日志或 Compose 文件；
- API、task-worker、render-worker、maintenance 使用不同的服务身份；
- 沙箱不挂载任何 Secret；
- 数据库账号至少拆分为迁移账号和应用运行账号；
- 所有 Secret 必须有负责人、轮换周期和应急吊销流程。

## 6. 镜像构建与供应链

生产服务器不应直接从工作区构建镜像。CI 应完成：

1. 锁定依赖并执行后端测试、前端类型检查、测试和构建；
2. 构建 `agent` 与 `web` 镜像；
3. 扫描操作系统包、Python/Node 依赖和镜像漏洞；
4. 生成 SBOM；
5. 使用提交 SHA 和版本号双标签推送私有镜像仓库；
6. 对镜像签名；
7. 部署时只允许不可变 digest 或提交 SHA 标签。

建议标签：

```text
registry.example.com/eduflow/agent:git-<commit-sha>
registry.example.com/eduflow/web:git-<commit-sha>
```

仓库提供的 `ops/production/compose.production.yaml` 已把 `build:` 替换为 `image:`，并为
容器配置日志轮转，避免 JSON 日志耗尽宿主机磁盘。对应的环境模板是
`ops/production/stage1.env.example`。

## 7. 首次部署流程

### 7.1 基础设施准备

1. 创建隔离的 staging 与 production 网络/账号。
2. 创建 PostgreSQL、Redis、对象存储、KMS、Secret Manager 和 SMTP 配置。
3. 为应用创建最小权限身份和安全组。
4. 创建 DNS、TLS 证书、WAF 和负载均衡器。
5. 创建应用主机，仅允许负载均衡器访问 Web 端口。
6. 挂载独立数据盘用于容器数据、共享沙箱目录和临时渲染文件。
7. 设置 CPU、内存、磁盘、证书和备份健康告警。

### 7.2 发布前检查

在 CI 或隔离构建环境执行：

```bash
cd agent
pytest

cd ../web
npm ci
npm run verify
```

然后在 staging 使用最终镜像执行数据库迁移预检和应用启动校验。

### 7.3 数据库迁移

每次发布只运行一次：

```bash
docker compose --env-file /etc/eduflow/production.env \
  -f docker-compose.yml \
  -f ops/production/compose.production.yaml \
  run --rm migrate
```

迁移成功后再更新 API 和 Worker。迁移必须保持向后兼容，直到旧版本容器全部退出；禁止在
一次发布中同时做不可逆字段删除和应用切换。

### 7.4 启动顺序

1. 数据库迁移；
2. `material-sandbox`；
3. `agent-api`；
4. `web`；
5. `task-worker`；
6. 单实例 `maintenance`；
7. 可观测性组件；
8. 可选的 `render-sandbox` 与 `render-worker`。

阶段一标准发布可以直接执行：

```bash
ops/production/scripts/deploy.sh /etc/eduflow/production.env
```

首次启动保持：

```dotenv
AUTH_ALLOW_REGISTRATION=false
VIDEO_PUBLIC_ENABLED=false
```

### 7.5 管理员引导

如果系统尚未存在管理员：

1. 临时允许指定来源进行注册，或在受控 staging 完成账号创建；
2. 创建目标账号；
3. 在使用同一数据库的 API 环境执行：

```bash
python -m scripts.bootstrap_admin --email admin@example.com
```

4. 重新登录并验证管理员页面；
5. 关闭临时注册入口，再按运营计划决定是否开放公开注册。

## 8. 发布后验收

### 8.1 基础健康检查

```bash
curl -fsS https://app.example.com/api/health
curl -fsS https://app.example.com/api/ready
```

确认公网访问下列地址返回 404 或拒绝访问：

```text
/docs
/openapi.json
/api/metrics
/api/metrics/prometheus
```

### 8.2 业务验收

- 注册关闭状态符合预期；
- 邮箱验证、登录、退出和会话撤销正常；
- 管理员与普通用户权限隔离正常；
- 用户 A 不能访问用户 B 的项目、素材、版本、任务或审计事件；
- BYOK 凭据可以保存、轮换、解密和调用；
- 全局模型 Key 为空时仍能通过用户凭据完成生成；
- 生成过程可进入人工审批并恢复；
- SSE 断开后能按游标继续，不重复提交任务；
- 材料上传、解析、引用和删除正常；
- 配额、限流、429 响应和并发限制符合配置；
- 账户删除流程能够清理 checkpoint、对象和会话。

### 8.3 故障与容量验收

在专用 staging 环境运行，不要对生产环境执行故障注入：

```bash
python agent/scripts/http_capacity_smoke.py \
  --duration 60 --concurrency 16 \
  --report capacity-smoke-report.json

python agent/scripts/compose_fault_smoke.py \
  --services redis postgres minio \
  --report fault-smoke-report.json
```

验收目标应至少包含：

- 健康端点 p95 延迟与错误率；
- 生成成功率、p50/p95 耗时；
- LLM 429/5xx 与重试率；
- SSE 重连成功率；
- 队列最老任务年龄；
- Worker lease 过期率；
- 材料解析和视频渲染失败率；
- 每用户和全系统成本上限是否生效。

## 9. 可观测性与告警

### 9.1 指标

Prometheus 应通过内部网络直接抓取 API，并从 Secret Manager 挂载 bearer token 文件。
公网 Nginx 不代理 metrics。

至少监控：

- HTTP 请求量、p95/p99、4xx、5xx；
- 登录失败、注册挑战失败和可疑来源；
- PostgreSQL 连接、慢查询、锁、复制延迟、存储；
- Redis 延迟、连接、内存和淘汰；
- LLM/Embedding 调用量、延迟、429、5xx、token 和成本；
- KMS wrap/unwrap 失败和延迟；
- 队列长度、最老任务年龄、lease 过期和重试；
- SSE 活动连接、断线和重放事件量；
- 材料/导出对象数量与存储增长；
- 容器重启、OOM、CPU、内存、磁盘 inode；
- 备份、PITR、对象版本控制和遥测中断。

### 9.2 日志与追踪

- 使用结构化 JSON 日志；
- 每条请求携带 request/trace ID；
- API、Worker、KMS Bridge 和外部模型请求使用同一 trace 上下文；
- 日志中清除 Cookie、Authorization、模型 Key、材料正文和用户敏感字段；
- OpenTelemetry SDK 发送到内网 Collector；
- Collector 再转发到选定的指标、日志和追踪后端；
- 初始 trace 采样率可设为 10%，错误请求保留更高采样率。

每个告警必须有负责人、严重级别、通知通道和 Runbook。没有负责人和处理动作的告警不应
作为正式上线门禁的一部分。

## 10. 备份与恢复

### 10.1 PostgreSQL

- 多可用区部署；
- 连续 WAL 归档/PITR，目标 RPO 不超过 15 分钟；
- 每日保留备份；
- 备份使用与应用 Secret 不同的加密密钥；
- 每月恢复到隔离账号/网络并记录实际 RPO/RTO。

### 10.2 对象存储

- 开启版本控制；
- 开启服务端加密；
- 删除操作保留恢复窗口；
- 审计归档启用不可变保留；
- 定期抽样下载 materials 与 exports，并核对数据库元数据。

### 10.3 恢复演练

每月至少执行：

1. 从备份恢复 PostgreSQL；
2. 使用目标发布镜像执行 Alembic；
3. 运行 `python -m scripts.audit_artifact_consistency`；
4. 抽查素材、导出物和签名链接；
5. 验证审计归档 hash chain/HMAC；
6. 验证 KMS 旧版本仍可解包历史凭据；
7. 记录恢复完成时间和数据缺口。

正式目标：RPO 不超过 15 分钟，服务 RTO 不超过 2 小时。

## 11. 发布、灰度与回滚

### 11.1 常规发布

1. CI 产出并扫描不可变镜像；
2. 部署到 staging；
3. 执行离线测试、迁移测试、容量 smoke 和真实供应商小样本验证；
4. 备份生产数据库并确认 PITR 正常；
5. 执行生产迁移 Job；
6. 发布一个 canary API，保持注册和视频关闭；
7. 验证 readiness、KMS、SMTP、BYOK、SSE、队列和告警；
8. 滚动替换其余 API；
9. 更新 task-worker；
10. 最后更新 maintenance 和视频 Worker。

### 11.2 应用回滚

- 保留上一版本镜像 digest 和配置快照；
- readiness 或关键业务指标不达标时停止继续发布；
- 回滚应用镜像，不自动回滚数据库；
- 数据库变更必须保持至少一个旧应用版本可运行；
- 若迁移本身失败，停止发布并从迁移前快照/PITR 恢复到隔离环境分析，不能直接在生产库
  反复执行未经验证的修复语句。

## 12. 安全基线

- 所有容器以非 root 用户运行；
- 根文件系统尽量只读，临时写入使用受限 tmpfs；
- 删除全部 Linux capabilities，并启用 `no-new-privileges`；
- 沙箱禁用网络，且不注入任何服务凭据；
- 主机 Docker socket 不挂入业务容器；
- 禁止特权容器和 host network；
- 镜像按计划重建，不只在容器中临时升级软件包；
- WAF 限制异常请求、扫描和注册攻击；
- 管理员启用 MFA；
- 邮件验证和注册挑战在公开注册前启用；
- 材料上传维持 50 MB 边缘与应用双重限制；
- 对象下载使用短期签名 URL；
- 定期运行依赖、镜像、Secret 和 IaC 扫描；
- 对数据导出、角色变更、凭据操作和账户删除保留审计记录。

## 13. 阶段二：多副本演进条件

只有在下列条件完成后，才建议迁移 Kubernetes 或同类多节点平台：

1. 材料沙箱和渲染沙箱不再依赖单机 Docker volume，或者已经验证可靠的 RWX 存储；
2. API、Worker、maintenance 使用不同工作负载身份；
3. 默认拒绝 ingress/egress 的 NetworkPolicy 实际由 CNI 执行；
4. 沙箱使用独立 namespace、Restricted Pod Security 和专用节点池/RuntimeClass；
5. 数据库迁移实现独立 Job 和部署互斥；
6. task-worker 与 render-worker 有基于队列年龄和资源的扩缩容策略；
7. maintenance 被硬性限制为一个实例；
8. SSE 经 Ingress 和 CDN 完成长连接、缓冲关闭与断线重放测试；
9. 所有持久状态均已离开应用节点；
10. 恢复演练和多可用区故障演练已经通过。

目标形态：

- Web 静态文件进入 CDN；
- API 至少两个副本，跨可用区部署；
- task-worker 根据最老任务年龄扩缩容；
- render-worker 使用独立计算节点；
- 每个沙箱按任务创建短生命周期实例；
- PostgreSQL、Redis、对象存储、KMS 和可观测性全部托管或高可用化。

## 14. 上线门禁清单

### 基础设施

- [ ] 域名、TLS、WAF、负载均衡器已就绪；
- [ ] 数据库支持 pgvector，并启用多可用区与 PITR；
- [ ] Redis 不可公网访问并启用认证/加密；
- [ ] 对象存储启用版本控制、加密和生命周期；
- [ ] 应用主机只开放必要端口；
- [ ] Secret Manager 和 KMS Bridge 已完成审计测试。

### 应用

- [ ] 生产配置通过启动时 fail-closed 校验；
- [ ] 全局 LLM/Embedding Key 为空；
- [ ] API 文档和指标没有暴露公网；
- [ ] migration Job 成功；
- [ ] maintenance 只有一个实例；
- [ ] 沙箱无网络、无凭据、非 root、只读根文件系统；
- [ ] 管理员、注册、邮箱、MFA 和 BYOK 完成验收；
- [ ] SSE 断线恢复完成验收；
- [ ] 配额和限流完成验收；
- [ ] 视频保持关闭，直到独立容量和安全验收通过。

### 运维

- [ ] 日志、指标、追踪可以关联查询；
- [ ] 所有关键告警有负责人和 Runbook；
- [ ] 已验证数据库与对象存储备份；
- [ ] 已完成一次隔离恢复并记录 RPO/RTO；
- [ ] 已保留上一版本镜像和配置快照；
- [ ] 已演练回滚和依赖故障；
- [ ] 已建立密钥轮换和应急吊销流程。

## 15. 推荐实施节奏

### 第一周：staging

- 创建托管数据服务与应用主机；
- 完成 Secret、KMS Bridge、SMTP、TLS 和镜像流水线；
- 部署全部非视频服务；
- 完成迁移、权限、BYOK、SSE 和材料解析验收。

### 第二周：运维门禁

- 接入指标、日志、追踪与告警；
- 执行容量 smoke 和故障注入；
- 完成数据库、对象存储和审计归档恢复演练；
- 修正 p95 延迟、资源上限和连接池配置。

### 第三周：受控生产

- 关闭公开注册，邀请少量内部用户；
- 观察生成成本、队列年龄、错误率和用户隔离；
- 开放邮箱验证后的注册；
- 保持视频功能关闭或仅对白名单开放。

### 后续：视频与多副本

- 单独完成视频容量与安全测试；
- 开放低配额视频任务；
- 当单节点成为明确瓶颈时，再按第 13 节推进多副本改造。
