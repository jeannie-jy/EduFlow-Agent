## 1. 设计总则

### 1.1 核心原则

1. **需求驱动，不做预设**：每个设计决策对应需求文档中的具体条目，不提前为"可能的需求"做工程储备
2. **Agent 思考，确定性系统执行**：LLM 负责规划与生成结构化 DSL，渲染端（Web / Manim）是确定性解释器，不依赖 LLM 实时推理
3. **Multi-Agent 协作，非单体调用链**：各 Agent 有独立的系统提示词和职责边界，通过共享状态协作，而非一个 Agent 串行调 tool
4. **优先复用，聚焦差异化**：通用能力用成熟方案，核心创新点（DSL 驱动的双路径渲染、教学策略自主规划）自研

### 1.2 关键边界

| 做 | 不做 |
|----|------|
| Multi-Agent 教学推演生成 | 跨语言异构架构（MVP 全 Python） |
| DSL 驱动的 Web + Manim 双路径渲染 | MCP Server 独立部署（Tool 预留 MCP 兼容接口即可） |
| pgvector 知识库 + 会话级工作记忆 | 三层记忆系统（短期记忆层用 Redis 缓存覆盖） |
| 领域插件扩展点设计 | 多领域插件实现（MVP 只做 CS） |
| 结构化评估体系 | 全自动 Benchmark 平台（手工 + 脚本验证即可） |
| LangGraph Agent 编排 | 自研 Agent Runtime |

## 3. Multi-Agent 设计

### 3.1 Agent 角色定义

需求文档定义了 8 个 Agent 角色，其中 7 个为 LLM Agent，1 个为确定性转换器：

#### Agent-1: 教学规划 Agent (Planner)

| 项目 | 内容 |
|------|------|
| **职责** | 判断学习者水平、生成教学目标、识别先修知识、选择教学路径、决定讲解顺序 |
| **输入** | 用户主题、上传材料解析结果、教师约束、目标年级 |
| **输出** | 教学目标列表、知识点大纲、难度曲线、推演策略、内容风险点 |
| **调用的 Tool** | `search_knowledge`、`parse_material` |
| **触发时机** | 用户发起新推演请求 |

#### Agent-2: 知识解析 Agent (Knowledge)

| 项目 | 内容 |
|------|------|
| **职责** | 从文本/PDF/代码中抽取知识点、构建概念关系图、识别公式/伪代码/状态变量、标注易错点 |
| **输入** | Planner 输出的知识点大纲、原始输入材料 |
| **输出** | 概念节点列表、关系边、前置依赖图、关键术语表、可视化对象候选、可交互参数候选 |
| **调用的 Tool** | `search_knowledge`、`extract_concepts` |
| **触发时机** | Planner 完成教学计划后 |

#### Agent-3: 推演编排 Agent (Coder)

| 项目 | 内容 |
|------|------|
| **职责** | 将知识点拆成逐帧序列、为每帧定义画面元素/状态变化/讲解文本/交互逻辑、保证帧间状态一致性、生成标准 DSL JSON |
| **输入** | Knowledge Agent 输出的概念关系图、Planner 输出的教学策略 |
| **输出** | 完整的 RenderScript DSL (含 frames 数组、parameters、assets) |
| **调用的 Tool** | `design_parameters`、`generate_asset` |
| **触发时机** | Knowledge Agent 完成后 |

#### Agent-4: 参数设计 Agent (Parameter)

| 项目 | 内容 |
|------|------|
| **职责** | 根据知识点类型生成可调参数、区分教师/学生参数等级、定义取值范围和边界条件、生成参数变更后的状态重算逻辑 |
| **输入** | Coder 当前生成的帧序列、Knowledge Agent 的知识概念列表 |
| **输出** | 参数定义列表 (含名称、类型、默认值、范围、重算影响范围) |
| **触发时机** | 作为 Coder Agent 的 Tool 按需调用，也可独立被用户触发 |

#### Agent-5: 多模态资源 Agent (Resource)

| 项目 | 内容 |
|------|------|
| **职责** | 生成知识卡片、思维导图、状态表、伪代码区块、可视化资源描述 |
| **输入** | Knowledge Agent 的概念输出、Coder Agent 的帧上下文 |
| **输出** | 资源描述对象 (card / mindmap / table / code_block 等)，嵌入帧的 visual_objects |
| **触发时机** | 作为 Coder Agent 的 Tool 按需调用 |

#### Agent-6: 质量评估 Agent (Quality)

| 项目 | 内容 |
|------|------|
| **职责** | 检查事实正确性、教学目标覆盖度、帧间状态一致性、参数有效性、DSL Schema 合法性、表达难度适配 |
| **输入** | Coder 输出的完整 DSL |
| **输出** | 评分 (正确性/清晰度/连贯性/可交互性/可渲染性/教学完整性) + 问题列表 + 修复建议 |
| **触发时机** | Coder 完成帧生成后自动触发 |

#### Agent-7: 反思修订 Agent (Reflection)

| 项目 | 内容 |
|------|------|
| **职责** | 根据质量报告和用户反馈生成修订计划、对低分片段局部重写、保留人工锁定内容、记录修订原因 |
| **输入** | Quality Agent 的质量报告、用户反馈记录、当前 DSL |
| **输出** | 修订后的 DSL、修订差异记录 |
| **触发时机** | Quality 评分低于阈值，或用户主动发起修订 |

#### 确定性组件: Manim 生成管线 (非 Agent)

Manim 代码生成提供**双路径**，按场景选择：

**路径 A — 确定性转换** (`manim_adapter.py`)：
- DSL 中每种 `visual_object.type` 有固定的 Manim Mobject 映射
- DSL 中每种 `animation.type` 有固定的 Manim Animation 映射
- 输出为完整的 Manim Python 脚本，规则驱动、速度快

**路径 B — LLM 驱动生成** (`manim_llm_adapter.py`)（当前默认）：
- LLM 根据教学语义自主设计可视化布局、配色方案和动画编排
- 将 DSL 帧序列 + 教学计划作为上下文，生成更自然的教学视频脚本
- 生成后经 `manim_validator.py` 6 项质量检测（语法、MathTex+CJK、无效 lexer、Code API、r-string 转义、construct 内 print）
- 常见 Manim API 问题自动修复（`Code(code=…)` → `code_string=…`、Code 上的 font_size、无效 language）
- 生成失败时自动将错误反馈给 LLM，重试一次

**渲染与容错**：
- 视频渲染在独立线程 (`ThreadPoolExecutor`) 中执行，不阻塞 FastAPI 事件循环
- Manim 渲染后若未产出最终 MP4，自动通过 FFmpeg concat 合并 `partial_movie_files`
- 支持 Redis Worker（Docker）和进程内 fallback 两种渲染模式

### 3.2 Agent 协作流程 (LangGraph)

```
                    ┌─────────────┐
                    │   START     │
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │  Planner    │
                    │  Agent      │
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
              ┌─────┤ Human       ├─────┐
              │     │ Approval    │     │
              │     └─────────────┘     │
          (修改)                     (确认)
              │                        │
              └────────┬───────────────┘
                       │
                ┌──────▼──────┐
                │  Knowledge  │
                │  Agent      │
                └──────┬──────┘
                       │
                ┌──────▼──────┐
                │  Coder      │────► Parameter Agent (Tool)
                │  Agent      │────► Resource Agent (Tool)
                └──────┬──────┘
                       │
                ┌──────▼──────┐
                │  Quality    │
                │  Agent      │
                └──────┬──────┘
                       │
                 ┌─────▼──────┐
                 │ score>=阈值? │
                 └─────┬──────┘
                   │       │
                  YES     NO
                   │       │
                   │  ┌────▼───────┐
                   │  │ Reflection │──► Coder (重生成)
                   │  │ Agent      │
                   │  └────────────┘
                   │
            ┌──────▼──────┐
            │  输出 DSL    │
            └──────┬──────┘
                   │
            ┌──────▼──────┐
            │    END      │
            └─────────────┘
```

**关键设计决策：**

- **Human Approval 节点**：Planner 输出的教学计划在进入 Coder 前中断，等待用户确认。这是需求文档 7.1 节"用户确认或编辑计划"的技术实现
- **Reflection 循环**：Quality 不通过时触发 Reflection Agent 分析原因 → 调整策略 → Coder 重生成。循环上限 3 次
- **Coder 的 Tool 调用**：Parameter Agent 和 Resource Agent 设计为 Coder 可调用的子 Agent，而非独立节点，因为在生成帧的过程中需要灵活调用

### 3.3 Agent 间通信：共享 State

所有 Agent 在同一 LangGraph 进程内运行，通过 TypedDict State 共享上下文，而非 A2A 协议：

```python
class AgentState(TypedDict):
    # 用户输入
    user_input: str
    materials: list[dict]         # 上传材料解析结果
    constraints: dict             # 教师约束

    # Planner 产出
    teaching_plan: dict           # 教学目标、大纲、策略

    # Knowledge 产出
    knowledge_graph: dict         # 概念节点 + 关系边
    key_terms: list[str]

    # Coder 产出
    dsl: dict                     # 完整 RenderScript

    # Quality 产出
    quality_report: dict          # 评分 + 问题列表

    # Reflection 状态
    reflection_count: int
    revision_history: list[dict]

    # Human-in-the-Loop
    pending_approval: str | None  # 等待审批的内容
    user_feedback: dict | None    # 用户反馈

    # 元信息
    project_id: str
    status: str                   # drafting / planning / generating / reviewing / done
```

### 3.4 渐进式实施策略

| 阶段 | Agent 拆分程度 | 说明 |
|------|---------------|------|
| **原型 (V0.1)** | 2 Agent: Planner + Coder | Planner 兼任 Knowledge；Quality 用 Schema 校验代替；先跑通 DSL 生成 |
| **MVP (V0.5)** | 5 Agent: Planner, Knowledge, Coder, Quality, Reflection | Parameter 和 Resource 作为 Coder 的 Tool |
| **完整版 (V1.0)** | 7 Agent 全部独立 | Parameter 和 Resource 在需要更复杂策略时独立为 Agent |

## 4. 工具生态系统

### 4.1 工具清单


## 5. DSL 设计

### 5.1 定位

DSL 是系统的**核心创新点和唯一数据枢纽**。Agent 只输出 DSL，不感知前端或 Manim 的具体实现。Web Renderer 和 Manim Adapter 各自消费同一份 DSL。

### 5.2 顶层结构

```json
{
  "project_id": "proj_001",
  "topic": "Dijkstra Algorithm",
  "audience": "undergraduate_cs",
  "difficulty": "intermediate",
  "teaching_strategy": {
    "objectives": ["理解最短路径概念", "掌握 Dijkstra 算法贪心策略"],
    "prerequisites": ["图的邻接表表示", "贪心算法基本思想"],
    "approach": "先直观演示图遍历 → 引入距离表 → 逐步松弛 → 伪代码对照 → 复杂度分析"
  },
  "knowledge_graph": {
    "concepts": [
      {"id": "c1", "name": "最短路径", "type": "definition"},
      {"id": "c2", "name": "松弛操作", "type": "core_mechanism"}
    ],
    "edges": [{"from": "c1", "to": "c2", "relation": "leads_to"}]
  },
  "parameters": [
    {
      "key": "graph_data",
      "label": "图结构",
      "type": "graph",
      "default": {"nodes": 6, "edges": [...]},
```


#### 7.1.2 播放状态机

播放器核心是一个有限状态机，每个状态对应一种用户交互模式：

```
                    ┌──────────┐
           ┌──────►│  空闲     │◄─────────┐
           │       │ (IDLE)   │           │
           │       └─────┬────┘           │
           │             │ 点击播放        │
           │       ┌─────▼────┐           │
           │       │  播放中   │           │
           │       │ (PLAYING) │           │
           │       └─────┬────┘           │
           │       │     │     │          │
           │  暂停/点击   │  到达关键帧     │
           │       │     │     │          │
           │  ┌────▼─┐ ┌─▼───────┐       │
           │  │暂停   │ │ 交互等待  │      │
           │  │(PAUSE)│ │(WAITING) │      │
           │  └───────┘ └────┬─────┘      │
           │                 │ 用户完成交互 │
           │                 │             │
           │          参数变更触发重算      │
           │                 │             │
           │          ┌──────▼─────┐       │
           └──────────│  重算中     │───────┘
                      │(RECOMPUTE) │
                      └────────────┘
```

**交互等待 (WAITING)** 是关键状态：当帧定义了 `interaction_hooks`（如 quiz、参数调节），播放器暂停自动播放，等待用户操作后继续。这是"交互式推演"区别于视频的本质——用户不是被动观看，而是在关键节点参与其中。

#### 7.1.3 逐帧过渡模型

从帧 N 到帧 N+1 的过渡流程：

```
帧 N 当前状态
    │
    ▼
1. 读取帧 N+1 的 animations 列表
    │
    ▼
2. 依次执行动画:
   ├── highlight 旧元素 → 持续 500ms
   ├── relax_edge → 持续 800ms
   ├── update_value → 触发状态表单元格闪烁
   └── appear 新元素 → fadeIn 300ms
    │
    ▼
3. 所有动画执行完毕后
   ├── 更新 visual_objects（新元素可见）
   ├── 更新 state_snapshot（状态表数据）
   ├── 更新 narration（讲解文本）
   └── 检查 checks（显示校验提示）
    │
    ▼
帧 N+1 稳定状态 → 等待下一帧或用户操作
```

### 7.2 参数交互系统

#### 7.2.1 参数修改 → 状态重算流程

这是交互式推演区别于视频的核心能力。用户在播放过程中修改参数，系统重算受影响帧的状态：

```
用户拖动 "边权重" 滑块
    │
    ▼
前端判断 recompute_scope:
    │
    ├── scope="local"  → 前端本地重算
    │   (仅影响当前帧的数值，如更改数组元素)
    │   → 更新 state_snapshot → 重新渲染当前帧
    │
    └── scope="all_frames" → 请求后端重算
        (影响帧序列结构，如更改图结构后需要重新跑算法)
        → POST /api/projects/{id}/recompute
        → Agent 重新生成受影响帧 → SSE 流式返回
        → 前端增量更新帧列表
```

| `string` | Input / Select | 起点选择 |
| `boolean` | Switch | 是否显示伪代码 |
| `enum` | RadioGroup / Select | 调度策略选择 |

| `code` | Monaco Editor 迷你模式 | 代码片段编辑 |

### 7.3 推演编辑

播放器和编辑器不是两套界面，而是**同一界面的两种模式**。用户在播放过程中随时可以进入编辑模式，编辑完继续播放。

#### 7.3.1 编辑模式 vs 播放模式

```
播放模式                          编辑模式
───────                          ───────
• 逐帧自动/手动推进               • 帧列表可拖拽排序、增删
• 可调参数（参数面板）              • 点击帧 → 属性面板可编辑
• 可答题（交互 quiz）              • 画布显示编辑手柄
• 可标注反馈                      • 支持局部重生成
                                  • 可锁定帧防止被 Agent 修改
```

#### 7.3.2 编辑操作分级

不是所有编辑都面向同一用户。按操作深度分级：

| 级别 | 操作 | 典型用户 |
|------|------|---------|
| **L1 交互** | 调节参数滑块、切换选项、拖拽图节点 | 学生/教师 |
| **L2 标注** | 修改讲解文本、标记问题、评分 | 学生/教师 |
| **L3 内容编辑** | 修改 visual_objects 样式和位置、编辑 state_snapshot | 教师/助教 |
| **L4 结构编辑** | 增删帧、调整帧顺序、锁定、触发重生成 | 教师 |

前端不按角色做硬隔离，而是将 L3/L4 操作默认折叠，需要时展开。

#### 7.3.3 编辑操作的影响范围

| 操作 | 影响范围 | 处理方式 |
|------|---------|---------|
| 修改讲解文本 | 仅当前帧 | 直接更新 DSL |
| 修改 visual_objects 样式 | 仅当前帧 | 直接更新 DSL |
| 修改 state_snapshot | 当前帧 + 后续帧 | 校验器检查不一致，标记 |
| 拖拽调整帧顺序 | 整个序列 | 重排 order_index |
| 锁定帧 | 仅当前帧 | Agent 重生成时跳过 |
| 局部重生成 | 指定帧范围 | 调用 regenerate 接口 |
| 修改参数定义 | 所有使用该参数的帧 | 触发重算 |

#### 7.3.4 锁定机制

用户对某帧加锁后，Reflection Agent 和局部重生成都**不得修改**被锁定的帧。以锁定帧的 `state_snapshot` 为边界约束重算后续帧。

```python
def regenerate_frames(project_id, scope, locked_frame_ids):
    for frame in scope:
        if frame.id in locked_frame_ids:
            continue
        frame = call_llm_to_regenerate(frame)
    reconcile_states(locked_frame_ids)
```

#### 7.4.2 LLM 代码生成详解

`manim_llm_adapter.py` 负责将教学 DSL 转化为 Manim 可视化脚本：

**输入**：DSL 帧序列 + teaching_plan（教学目标、策略、知识图谱）

**LLM Prompt 策略**：
- System prompt 包含完整 Manim API 参考（Mobject 类型、Animation 类型、布局建议）
- User message 传递 DSL 的 JSON 片段（每帧的 visual_objects、animations、narration）
- 明确约束：禁止 MathTex（中文环境使用 Text + Unicode）、禁止 Code 对象使用 `font_size`、使用 `code_string=` 参数

**自动修复**（`_fix_script` 阶段）：
- `Code(code=...)` → `Code(code_string=...)`（Manim v0.20+ API 兼容）
- 移除 Code 构造中的 `font_size` 参数
- 修正无效的 `language` 参数值（如 "c++" → "cpp"）

**重试机制**：生成后运行 Validator，发现 error 级别问题时将错误信息反馈给 LLM，最多重试 1 次（共 2 次尝试）。LLM 调用内置 120 秒超时 + 4 次 max_tokens 递增重试（8K→16K→32K→64K），防止无限循环。

#### 7.4.3 Validator 质量检测

`manim_validator.py` 对 LLM 生成的脚本执行 6 项静态检查：

| # | 规则 | 检测内容 | 严重度 |
|---|------|---------|--------|
| 1 | `syntax` | Python 语法是否正确（`compile()` 检查） | error |
| 2 | `no_mathtex_cjk` | MathTex 中是否包含中文字符（Manim 不支持） | error |
| 3 | `valid_lexer` | Code 对象的 language 参数是否为有效 Pygments lexer | error |
| 4 | `code_api` | 是否使用了已废弃的 `Code(code=...)` 而非 `Code(code_string=...)` | error |
| 5 | `rstring_escapes` | r-string 中是否包含结尾反斜杠（会导致语法错误） | warning |
| 6 | `no_print_in_construct` | `construct()` 方法中是否包含 `print()` 语句 | warning |

`has_errors()` 判断是否存在 error 级别问题，决定是否触发重试。

#### 7.4.4 渲染与容错

**线程隔离**：LLM 调用（`asyncio.run(convert_dsl_to_manim_llm(...))`）和 Manim 渲染（`subprocess.run`）都在 `ThreadPoolExecutor` 的独立线程中执行，FastAPI 事件循环不被阻塞。导出期间服务端 200 OK 正常响应。

**双模式渲染**：
- **Redis Worker 模式**（生产环境）：Worker 从 `manim:queue` 消费任务并立即写入 `claimed` 标记（TTL 600s），Docker 容器内执行
- **进程内 fallback**（开发环境 / Worker 不可用时）：等待 3 秒后检查 `claimed` 标记和 job 状态，未被消费则在当前进程的 `ThreadPoolExecutor`（max_workers=2）中处理。LLM 调用前通过 `asyncio.set_event_loop(asyncio.new_event_loop())` 隔离事件循环

**FFmpeg 分片合并**：Manim 在渲染复杂场景时可能生成 `partial_movie_files/` 目录（含多个片段 MP4），但未自动合并为最终文件。`_merge_partial_movies()` 扫描所有 `partial_movie_files` 目录，使用 FFmpeg concat demuxer 拼接：
```
ffmpeg -f concat -safe 0 -i _concat_list.txt -c copy output.mp4 -y
```
FFmpeg 路径通过 `_find_ffmpeg()` 统一查找（优先级：`FFMPEG_PATH` 环境变量 > 系统 PATH 中的 `ffmpeg`），避免硬编码平台特定路径。

**状态同步**：渲染进度实时写入 Redis (`manim:job:{job_id}`)，前端通过轮询 `GET /api/export/{job_id}` 获取进度百分比和产物下载链接。同时持久化到 DB（`export_jobs` 表）。

### 7.5 双路径关系

- **Web 推演是主产品**：所有设计和 Agent 产出的默认目标
- **Manim 视频是副产品**：同一份 DSL 的另一种消费方式，Agent 不用感知
- **Manim 生成策略**：默认使用 LLM 路径（教学语义 → 可视化设计），确定性路径作为快速回退
- **异步独立执行**：视频渲染在独立线程或 Docker Worker 中跑，不阻塞 Web 交互
- **独立降级**：任一路径失败不影响另一路径

- 数据库对象：B+ 树、事务时间线、查询计划树

## 9. 技术选型

### 9.1 选型总表

| 层次 | 选型 | 核心理由 |
|------|------|---------|
| **LLM** | DeepSeek-Coder-V3 (主) / Qwen2.5-Coder-7B (轻量) | 兼容 OpenAI API；Coder 模型在代码/结构化生成上表现好 |
| **Embedding** | text-embedding-3-small (1536维) | 性价比最优 |
| **Agent 编排** | **LangGraph** | StateGraph 原生支持条件路由 + Human-in-the-Loop + 状态持久化 |
| **后端** | Python 3.12+ / FastAPI | 异步高性能；与 ML/AI 工具链无缝；SSE 流式推送 |
| **数据库** | PostgreSQL 16 + pgvector | 关系数据 + 向量检索统一存储，减少运维复杂度 |
| **缓存/队列** | Redis 7 | 渲染任务队列 (BullMQ 模式) + 会话缓存 |
| **文件存储** | MinIO (S3 兼容) | 上传素材、Manim 渲染产物、DSL 导出文件 |
| **前端** | React 18 + TypeScript + Vite | 生态最成熟、React Flow 生态好 |
| **图渲染** | React Flow | 专为交互式图结构设计，避免从零写布局算法 |
| **动画** | framer-motion + Canvas 2D | 声明式过渡 + 自定义逐帧绘制互补 |
| **代码展示** | Monaco Editor (编辑) / Shiki (高亮) | 接近 VS Code 体验 |
| **视频渲染** | Manim CE + FFmpeg (Docker) | 需求文档指定 |
| **部署** | Docker Compose | MVP 单机部署，无 K8s 必要 |

### 9.2 为什么选择 LangGraph

| 考量 | 分析 |
|------|------|
| **Multi-Agent 编排** | StateGraph 的节点 + 条件边模型天然匹配 Agent 协作流程（3.2 节流程图） |
| **Human-in-the-Loop** | `interrupt()` 机制原生支持"生成计划 → 等待确认 → 继续执行" |
| **状态持久化** | 内置 checkpointer，AgentState 可序列化到 Postgres，支持暂停恢复 |
| **流式输出** | Native streaming，前端可实时展示生成进度 |
| **生态** | LangSmith 可观测性（可选启用），社区活跃 |

### 9.3 为什么不用 MCP Server / A2A

- 所有 Agent 在同一进程内运行，共享 State 通信即可，不需要进程间通信协议
- Tool 的接口设计（4.2 节）与 MCP Tool 规范对齐，未来如需拆分为独立服务，改造代价低
- MVP 阶段不引入额外的协议层复杂度

### 10.2 核心表

```sql
-- 项目
CREATE TABLE projects (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    title VARCHAR(500) NOT NULL,
    topic VARCHAR(300),
    audience VARCHAR(100) DEFAULT 'undergraduate_cs',
    difficulty VARCHAR(50) DEFAULT 'intermediate',
    status VARCHAR(50) DEFAULT 'draft',
    dsl_snapshot JSONB,          -- 最新 DSL 的快照
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW()
);

-- 帧 (核心表，高频读写)
CREATE TABLE frames (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    project_id UUID REFERENCES projects(id) ON DELETE CASCADE,
    version INT NOT NULL DEFAULT 1,
    order_index INT NOT NULL,    -- 帧序号
    title VARCHAR(500),
    learning_goal TEXT,
    narration TEXT,
    visual_objects JSONB,        -- 画面元素定义
    state_snapshot JSONB,        -- 状态快照
    animations JSONB,            -- 动画序列
    interaction_hooks JSONB,     -- 交互控件
    checks JSONB,                -- 校验规则
    quality_status VARCHAR(50) DEFAULT 'pending',
    is_locked BOOLEAN DEFAULT FALSE,
    UNIQUE (project_id, version, order_index)
);

-- 参数
CREATE TABLE parameters (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    project_id UUID REFERENCES projects(id) ON DELETE CASCADE,
    key VARCHAR(200) NOT NULL,
    label VARCHAR(500),
    param_type VARCHAR(50),      -- number / string / boolean / enum / graph / array
    default_value JSONB,
    current_value JSONB,
    constraints JSONB,           -- 取值范围、边界条件
    visibility VARCHAR(50) DEFAULT 'student',
    recompute_scope JSONB        -- 参数变更影响范围
);

-- 质量报告
CREATE TABLE quality_reports (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    project_id UUID REFERENCES projects(id) ON DELETE CASCADE,
    version INT NOT NULL,
    scores JSONB,                -- {correctness: 0.9, clarity: 0.85, ...}
    issues JSONB,                -- [{frame_id, type, severity, description}]
    suggestions JSONB,
    is_blocking BOOLEAN DEFAULT FALSE,
    created_at TIMESTAMPTZ DEFAULT NOW()
);

-- 导出任务
CREATE TABLE export_jobs (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    project_id UUID REFERENCES projects(id) ON DELETE CASCADE,
    target VARCHAR(50) NOT NULL,  -- manim_video
    status VARCHAR(50) DEFAULT 'queued',
    config JSONB,                 -- 分辨率、帧率、格式等
    progress_pct FLOAT DEFAULT 0,
    artifacts JSONB,              -- 产物路径列表
    error_log TEXT,
    created_at TIMESTAMPTZ DEFAULT NOW(),
    completed_at TIMESTAMPTZ
);
```

### 10.3 索引策略

```sql
-- 帧查询：按项目和序号
CREATE INDEX idx_frames_project_order ON frames (project_id, version, order_index);

-- 参数查询：按项目

-- 质量报告：按项目和时间
CREATE INDEX idx_quality_project ON quality_reports (project_id, created_at DESC);

-- 导出任务：按状态 (队列轮询)
CREATE INDEX idx_export_status ON export_jobs (status, created_at);

    USING ivfflat (embedding vector_cosine_ops);
CREATE INDEX idx_kb_tags ON knowledge_base USING gin (tags);
```

## 13. 质量保障

### 13.1 多层校验体系

```
Layer 1: Schema 校验 (确定性的)
  └── Pydantic 模型验证 DSL 结构完整性、类型正确性

Layer 2: 逻辑一致性校验 (部分确定性 + 部分 LLM)
  └── 帧间状态一致性、参数合法性、动画时长合理性

Layer 3: 教学质量评估 (LLM)
  └── Quality Agent: 六维度评分 + 问题定位
      正确性/清晰度/连贯性/可交互性/可渲染性/教学完整性

Layer 4: 人工反馈 (Human)
  └── 帧级标注 + 评分 + 修改建议
```

### 13.2 评估方式

| 方式 | 用途 | 频率 |
|------|------|------|
| **Schema 校验** | 每次 DSL 输出自动执行 | 每次生成 |
| **Golden Case 回归** | 20 个预置知识点的手工验证用例 | 发版前 |
| **用户评分** | 在线收集用户对推演质量的评分 (1-5) | 持续 |
| **人工抽查** | 团队成员定期抽查生成质量 | 每周 |

### 13.3 质量阈值

| 指标 | 阈值 | 动作 |
|------|------|------|
| Schema 校验失败 | 任何 | **阻塞**：不进入渲染，直接触发修正 |
| 帧间状态不一致 | 任何 | **阻塞**：禁止导出视频 |
| Quality 综合评分 | < 60% | **阻塞**：触发 Reflection Agent |
| Quality 综合评分 | 60-80% | **警告**：标记问题但允许预览 |
| Quality 综合评分 | > 80% | **通过** |

## 15. 非功能需求对策

| 需求 | 目标 | 实现方式 |
|------|------|---------|
| 计划生成延迟 | < 30s | LLM streaming + 分阶段返回 |

| 渲染隔离 | — | Docker 容器 + CPU/内存限制 + 超时 (10min) |

## 附录 A：与旧设计文档 (v2.2) 的核心差异

| 维度 | 旧 v2.2 | 新 v1.0 | 调整原因 |
|------|---------|---------|---------|
| Agent 数量 | 5 个 | 7 个 (+ Resource, Parameter) | 对齐需求文档的 8 Agent 定义 |
| Agent 编排 | LangGraph + Router | LangGraph + 条件边 | 保留，LangGraph 是正确选择 |
| 后端语言 | Python + Java | 纯 Python | MVP 不需要异构架构 |
| 通信 | gRPC + A2A + MCP | LangGraph 共享 State + HTTP/SSE | 同进程 Agent 不需要进程间协议 |
| 记忆 | 三层 (Working/Short/Long) | 知识库 + 工作记忆 | 两层够用，短期记忆用 Redis 缓存覆盖 |
| 前端 | Next.js 15 SSR | React 18 + Vite CSR | SSR 对交互式编辑器无增益 |
| 评估 | EduCS-Benchmark 100 场景 | Golden Case 20 例 + 用户评分 | Benchmark 是过度设计 |
| 部署 | K8s + GPU Node | Docker Compose | MVP 单机够用 |
| 可观测性 | OTEL + Prometheus + Grafana | 结构化日志 + LangSmith (可选) | 等有运维需求再加 |

核心思路不变：**Agent 思考、确定性执行、DSL 驱动双路径渲染。** 调整的是实施层面的复杂度——保留 Multi-Agent 架构亮点，去掉与核心创新无关的工程堆砌。
